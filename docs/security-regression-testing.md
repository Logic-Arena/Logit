# 보안 수정 검증

프로젝트 루트에서 Node.js 24로 실행합니다. 백엔드와 프론트엔드 의존성이 설치되어 있어야 합니다.

```powershell
npm.cmd run test:security
npm.cmd --prefix logic-arena-backend test
npm.cmd --prefix logic-arena-frontend run build
```

`fail 0`이면 검증한 방어 동작이 정상입니다. 이제는 취약한 요청이 성공하면 테스트가 실패합니다.
기존 `node tmp/security-review/audit.mjs`와 `prisma-filter.mjs`도 새 보안 검증을 실행합니다.

## 검증 범위

- 실제 서버의 REST 및 Socket.IO 라우터를 임시 loopback 포트에서 실행합니다.
- 운영 환경 파일을 읽지 않으며, DB와 AI는 합성 데이터 및 대역으로 교체합니다. 운영 DB 연결과 유료 AI 호출은 없습니다.
- 정상 로그인/가입/토론 제출/담당 학생 조회, 잘못된 토큰 거부, 복구 경로 차단, 서버에서 참가자 신원 결정, 비공개 방 보호, 요청 제한, 로그아웃과 세션 교체를 검사합니다.
- Google·Kakao 제공자 응답을 대역으로 바꿔 state의 브라우저·제공자 연결, 재사용·만료 거절, 쿠키 기반 일회성 교환을 검사합니다. 실제 제공자 계정의 동의 화면까지 자동 검증하는 것은 아닙니다.
- 관전자 재접속, 중복 투표, 평가 시작 후 입장, 마지막 유효 관전자 투표 전 종료 방지를 검사합니다.
- 실제 PostgreSQL 통합 테스트는 기본 실행에서 건너뜁니다. 배포 후 `src/maintenance/securitySmoke.js`가 임시 계정·학급·이력으로 실제 DB의 교사 권한 및 로그아웃을 검사하고 생성한 ID만 정리합니다. 유료 AI는 호출하지 않습니다.

## 브라우저에서 확인

기존 로컬 개발 환경에 DB와 환경변수가 준비되어 있다면 `npm.cmd start`로 실행합니다. 기존 서버가 실행 중이면 재시작합니다.

1. 기존 로그인 정보는 새 토큰 검증을 통과하지 않으므로 다시 로그인합니다.
2. 학생 계정 두 개를 서로 다른 브라우저 프로필에서 사용합니다. 한 계정으로 재로그인하면 이전 세션은 만료됩니다.
3. 방을 생성하고, 비밀번호가 있는 방에서 잘못된 비밀번호로 입장이 거절되는지 확인합니다.
4. 올바른 비밀번호로 입장한 두 사용자가 토론을 시작하고 글을 제출할 수 있는지 확인합니다.
5. 개발자 도구에서 `/api/rooms` 응답에 본문·평가·참가자 신원이 없고 참가자 수만 있는지 확인합니다.
6. 교사 계정은 담당 학급 학생의 평가만 조회할 수 있어야 합니다.

## 동작 변경과 운영 조건

- 아이디·이름만으로 비밀번호를 바꾸던 경로와 이메일로 아이디를 조회하던 공개 경로는 403으로 닫았습니다. 검증된 이메일 전송/본인 확인 기능이 아직 없으므로 로그인 화면에서 운영자 문의를 안내합니다. 이메일 복구 기능을 구현한 것은 아닙니다.
- 신규 비밀번호는 12자 이상, bcrypt 입력은 72바이트 이하여야 합니다. 기존 짧은 비밀번호는 로그인할 수 있습니다.
- 소켓은 최신 로그인 토큰으로 연결하며 참가자 ID와 이름은 서버가 결정합니다. 임의의 입장 닉네임은 받지 않습니다.
- 운영 `JWT_SECRET`은 32자 이상이어야 합니다. `TEACHER_CODE` 미설정 시 교사 가입이 거절됩니다.
- 인증 세션과 요청 제한은 현재 단일 백엔드 프로세스 메모리에 보관합니다. 재시작하면 재로그인이 필요하고 제한 카운터도 초기화됩니다. 여러 프로세스로 확장하기 전 공유 저장소로 전환해야 합니다.
- IP 기반 제한은 기본적으로 직접 연결된 IP를 기준으로 합니다. 현재 프록시 뒤에서는 여러 사용자가 같은 IP 한도를 공유할 수 있습니다. 임의의 `X-Forwarded-For`를 신뢰하도록 변경하지 않았습니다.

| 제한 | 기본값 |
| --- | --- |
| 로그인 | 계정별 15분 10회, 연결 IP별 15분 300회 |
| 회원가입 | 연결 IP별 시간당 20회 |
| 계정 복구 경로 | 연결 IP별 15분 10회 |
| 방 생성 | 계정별 10분 10회, 미종료 방 3개, 전체 방 500개 |
| 방 비밀번호 확인 | 계정별 분당 10회 |
| 소켓 입장 | 계정별 분당 15회 |
| 소켓 메시지 | 계정별 분당 240회, 본문 최대 20000자 |
| 토론 시작 | 계정별 시간당 6회 |
| AI 피드백 재요청 | 계정별 분당 3회, 같은 방 동시 생성 1개 |
| 직접 AI REST 요청 | 계정별 시간당 20회, 관련 API들이 한도 공유 |
| 전체 AI 서비스 작업 | 프로세스별 시간당 1000회, 동시 작업 16개 |

전체 AI 한도는 서비스 함수 호출 단위입니다. 함수 내부 재시도나 여러 모델 요청을 정확한 비용 단위로 집계하지 않으므로, 제공자 계정의 예산 제한도 별도로 설정해야 합니다.
이미 저장된 교사 요약 조회는 AI 한도를 사용하지 않습니다. 같은 이력의 요약을 생성 중이면 중복 생성 없이 대기 응답을 반환합니다.
